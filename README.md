# halyk-agent

Агент для Halyk AI Challenge: читает корпус обезличенных финансовых PDF и реестр транзакций,
и по каждому финансовому ковенанту каждого заёмщика определяет `status`, `actual` и
`evidence_txn_id`. Результат — `out/submission.json`.

## Архитектурный принцип

**LLM извлекает и классифицирует. Go считает и решает.**

Ни один агент не возвращает вердикт. Агенты производят три вида структурированных артефактов:

| Артефакт | Что это | Фаза |
|---|---|---|
| `CovenantSpec` | исполняемая спецификация пункта: **арифметическое выражение над именованными термами**, порог, оператор, период, carve-out'ы, триггер | 2 |
| `FactBase` | корректировки аудитора (реклассификации, отсечения, отклонённые), доли владения и порог связанности, курсы валют | 3 |
| `Label` | категория формулировки описания по таксономии + флаг связанной стороны на строке | 4 |

Дальше детерминированный движок на Go применяет спеки к размеченным данным: считает метрику в
`decimal`, проверяет триггер, применяет оговорки, сравнивает с порогом и выбирает evidence
методом leave-one-out. Модель никогда не складывает числа — для этого есть инструменты
`query_ledger` / `compute_metric`.

Причина в схеме оценки: ошибка в `status` обнуляет ячейку целиком, а `actual` оценивается по
линейной шкале с нулём при 5% отклонения. Арифметика в LLM — самый дешёвый способ потерять всё.

## Запуск

Секреты и настройки читаются из `.env` в рабочем каталоге (файл в `.gitignore`;
явный `export` всегда перекрывает его):

```bash
LLM_API_KEY=...
TEAM=...
CONTACT_EMAIL=...
MODEL=gemini-3.5-flash-lite
```

```bash
go build -o bin/halyk-agent ./cmd/halyk-agent

bin/halyk-agent llm-check   # проверка ключа, имени модели и обвязки провайдера одним запросом

bin/halyk-agent ingest      # фаза 0 — леджер, шаблон, текст всех документов (без LLM)
bin/halyk-agent triage      # фаза 1 — тип документа и его заёмщик
bin/halyk-agent covenants   # фаза 2 — CovenantSpec на каждый пункт + critic
bin/halyk-agent specs P1    # спеки заёмщика рядом с текстом пункта — для ручной сверки
bin/halyk-agent facts       # фаза 3 — отчётность, граф сущностей, FX
bin/halyk-agent classify    # фаза 4 — категория и связанность на каждой строке леджера
bin/halyk-agent labels P1   # размеченный леджер заёмщика: итоги по категориям и все строки
bin/halyk-agent evaluate    # фазы 5-6 — движок, evidence, критик по ячейкам; пишет out/review.md
bin/halyk-agent stability   # сколько ячеек держится при повторных прогонах модели
bin/halyk-agent submit      # фаза 7 — заполнение шаблона in-place
bin/halyk-agent report      # фаза 8 — финальный отчёт out/report.pdf (без LLM)
bin/halyk-agent run         # всё подряд

bin/halyk-agent validate    # проверка out/submission.json против шаблона
bin/halyk-agent score       # локальный скоринг против data/ground_truth.json (только для отладки)
bin/halyk-agent status      # что уже лежит в сторе
```

Каждая стадия резюмируется с того, что оставили предыдущие: состояние живёт в SQLite
(`.cache/halyk.db`), ответы LLM кэшируются по хешу промпта. Изменение фазы 5 не требует
повторного прогона фаз 1–4.

Молчаливых заглушек в коде нет: всё, что не посчиталось, названо в отчёте стадии поимённо.
Но и «упасть и ничего не отдать» стадия не может — по условию задачи пустая ячейка стоит ровно
столько же, сколько неверная, поэтому `run` доводит прогон до `out/submission.json` при любом
исходе: сбойная стадия деградирует, её ячейки остаются на baseline-заглушке, а код возврата
становится ненулевым и в конце печатается список деградировавших стадий. Критична только
`ingest` — без леджера и шаблона submission не из чего собрать.

Как деградируют стадии по отдельности:

| Стадия | Сбой одного элемента | Полный отказ стадии |
|---|---|---|
| `triage` | документ остаётся нераспознанным | дальнейшие модельные стадии пропускаются |
| `covenants` | ячейка без спеки → baseline | то же |
| `facts` | заёмщик без факт-базы | то же |
| `classify` | батч шаблонов размечается keyword-правилами | то же |
| `evaluate` | ячейка остаётся на baseline | submission из одних заглушек |

Исчерпание суточной квоты обрабатывается в одном месте — в клиенте LLM: после первого такого
ответа сетевые вызовы прекращаются до конца прогона, а закэшированные ответы продолжают
отдаваться, поэтому повторный запуск доигрывает по кэшу и не тратит квоту заново.

## Финальный отчёт

`report` собирает `out/report.pdf` — человекочитаемое досье на то, что ушло в submission.
Источник ответов — сам `out/submission.json` (файл, который и будет оценён), источник
обоснований — стор: спеки ковенантов, факт-базы, метки строк и трассы движка. Модель не
вызывается, так что отчёт можно перерисовывать сколько угодно.

Внутри: титул со сводными цифрами и описанием метода, таблица всех 36 ячеек, затем по каждому
заёмщику — счета, связанные стороны, курсы, корректировки аудитора, итоги размеченного леджера
и на каждый пункт: статус, `actual`, само выражение с порогом и периодом, термы, evidence
с расшифровкой транзакции, уверенность, реплика критика, цитата из договора и трасса вычисления.
Заканчивается приложением «Cells to check by hand» — ячейки с низкой уверенностью и те, с
которыми критик не согласился.

```bash
bin/halyk-agent report                       # out/report.pdf целиком
bin/halyk-agent report --only P1,B4          # только эти заёмщики
bin/halyk-agent report --file /tmp/p1.pdf    # другой путь
```

PDF пишется через `github.com/go-pdf/fpdf`; шрифты DejaVu вшиты в бинарник (`internal/report/fonts/`,
лицензия рядом) — цитаты договоров и названия компаний идут кириллицей, а результат не зависит от
шрифтов на машине. Текстовый слой в PDF есть: по отчёту работает поиск и `pdftotext`.

## Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `LLM_API_KEY` | ключ провайдера; нужен только LLM-стадиям (читается и `GOOGLE_API_KEY`) | — |
| `LLM_BASE_URL` | корень OpenAI-совместимого API | `https://generativelanguage.googleapis.com/v1beta/openai` |
| `MODEL` | модель для всех стадий; она же попадает в поле `model` submission | `gemini-3.5-flash-lite` |
| `REASONING_EFFORT` | `low\|medium\|high` или пусто — глубина рассуждения; flash-lite параметра не имеет | — |
| `LLM_SEED` | seed запроса или `none`; слой Gemini поля не принимает | `none` |
| `TEAM` | поле `team` в submission | `halyk-agent` |
| `CONTACT_EMAIL` | поле `contact_email` | — |
| `DATA_DIR` | каталог датасета | `./data` |
| `OUT_DIR` | каталог результатов | `./out` |
| `ARTIFACTS_DIR` | каталог артефактов | `./artifacts` |
| `CACHE_DIR` | каталог кэша страниц | `./.cache` |
| `LOG_DIR` | каталог дампов вызовов | `./logs` |
| `DB` | путь к SQLite-стору | `./.cache/halyk.db` |
| `MAX_CONCURRENCY` | лимит параллельных вызовов LLM | `4` |
| `RPM` | запросов в минуту (free tier Gemini даёт 15) | `14` |
| `RPH` | запросов в час; `0` — окна нет | `0` |
| `LOG_LEVEL` | `debug\|info\|warn\|error` — порог для stderr; в файл пишется всё | `info` |

Имена намеренно короткие. `.env` не перекрывает уже экспортированные переменные, поэтому
случайный `export MODEL=...` в оболочке имеет приоритет над файлом.

### Про лимиты

Планировщик умеет несколько окон сразу и берёт наибольший из интервалов: у Gemini часового окна
нет (`RPH=0`), поэтому темп задаёт `RPM` и пауза выходит ~4 с. У Cerebras окон пять, и часовое
жёстче минутного — 5 запросов в минуту дали бы 12 с, а 150 в час требуют 24 с; без учёта второго
окна стадия сожгла бы часовую квоту за полчаса и остаток часа простояла бы на 429.

Остаток квоты приходит в заголовках ответа и пишется в лог на уровне `debug`, а при подходе к
концу суточной нормы — предупреждением. Состояние живёт в SQLite, так что прерванный прогон
продолжается с того же места, а не начинается заново.

### Смена провайдера

Клиент говорит на OpenAI-совместимом `/chat/completions`, поэтому провайдер меняется тремя
переменными — `LLM_API_KEY`, `LLM_BASE_URL`, `MODEL` — без правки кода. Отличия слоёв учтены:
Gemini не принимает `seed` (`LLM_SEED=none`) и не знает `reasoning_effort` у flash-lite, а форму
её ошибок (`{"error":{...}}`, иногда в массиве, с задержкой в поле `retryDelay` вместо заголовка
`retry-after`) разбирает `parseAPIError`.

## Внешние зависимости

- **poppler** (`pdftotext`, `pdftoppm`) — обязательно.
- **tesseract** — обязательно: `gpt-oss-120b` текстовая, картинок не принимает, поэтому страницы
  без текстового слоя читаются только через OCR.
  `sudo pacman -S tesseract tesseract-data-rus tesseract-data-eng tesseract-data-kaz`
  Языки распознавания — `rus+eng+kaz` (см. `ASSUMPTIONS.md`, п. 10).

## Структура

```
cmd/halyk-agent/     точка входа
internal/config/     конфиг из окружения, пути, ключи
internal/domain/     типы: Txn, CovenantSpec, Verdict, Label, ...
internal/ingest/     фаза 0: CSV, шаблон, PDF → текст
internal/classify/   фаза 4: шаблоны описаний, правила, метки строк, связанные стороны
internal/engine/     фазы 5-6: термы, вычислитель выражений, вердикты, evidence leave-one-out
internal/evaluate/   стадия оценки: FX, прогон по ячейкам, критик, review.md
internal/stability/  проба стабильности: повторные прогоны мимо кэша, диф по ячейкам
internal/report/     фаза 8: сборка досье и вёрстка report.pdf, вшитые шрифты
internal/store/      SQLite: леджер, страницы, FTS, кэш LLM, артефакты
internal/llm/        клиент Cerebras chat/completions: кэш, дамп вызовов, rate limit
internal/cli/        cobra-команды по стадиям
data/                вход (в .gitignore)
out/                 submission.json, report.pdf, review.md, audit.jsonl
logs/                run.log (JSON, все уровни) и дампы вызовов модели
artifacts/           doc_index.json, specs/, facts/, labels/
```

## Состояние

- **M0 — скелет:** готово. CLI, конфиг, SQLite-стор с миграциями, кэш LLM, клиент провайдера.
- **M1 — ingest:** готово. 1473 транзакции, 12 заёмщиков, 36 ячеек, 202 документа, 845 страниц.
- **M2 — baseline submission:** готово. `run --deterministic` из чистого состояния даёт валидный
  `out/submission.json` (36/36 ячеек), проходящий `validate`; локальный скор 29.2%.
  Все ячейки помечены `source: "baseline"` — движок их перезапишет.
- **M3 — триаж и индекс документов:** готово. 202 документа классифицированы и привязаны
  к заёмщикам, `artifacts/doc_index.json`; проверка полноты проходит — у каждого из 12 заёмщиков
  есть действующий договор со всеми запрошенными пунктами.
- **M4 — извлечение ковенантов + critic:** готово. 36 спек для 12 заёмщиков в
  `artifacts/specs/<scenario>.json`; critic исправил 11 из 36. Спеки сверены с текстом
  договоров вручную (`halyk-agent specs <scenario>`).
- **M5 — факт-база:** готово. Корректировки аудитора, граф связанных сторон и курсы в
  `artifacts/facts/<scenario>.json`; страницы без текстового слоя прочитаны через OCR.
- **M6 — классификация:** готово. 675 строк двенадцати заёмщиков сводятся к 216 шаблонам
  описаний; правила и модель сошлись на 214, две спорные разобрала сильная модель, категорий
  `unknown` нет. Метки в `artifacts/labels/<scenario>.json`, шаблоны — в `_patterns.json`.
  Сверка с ground truth: платежи связанным сторонам и выручка совпадают до цента у всех
  заёмщиков, где пункт считается прямой суммой.
- **M7 — движок оценки и evidence:** готово. Все 36 ячеек считает детерминированный движок:
  арифметика над термами в `decimal`, период пункта, триггеры, оговорки, корректировки аудитора,
  выбор evidence методом leave-one-out. Локальный скор — **94.4%** (34.0/36): статус верен в
  34 ячейках, `evidence_txn_id` совпадает во всех 9, где ключ его требует. Две потерянные ячейки
  разобраны в `ASSUMPTIONS.md`, пп. 61–62.
- **M8 — верификация и полировка:** критик по ячейкам работает (`evaluate --critic`, включён по
  умолчанию): 36 ячеек прочитаны, несогласий 2. Проба стабильности (`stability --passes N`)
  реализована и протестирована, но цифр по ней нет — на прежней модели упёрлись в суточную квоту
  free tier. Подробности — `ASSUMPTIONS.md`, пп. 64–68.
- **M9 — финальный отчёт:** готово. `report` собирает `out/report.pdf` — 27 страниц: сводка по
  36 ячейкам и досье на каждого из 12 заёмщиков с цитатами договоров и трассами вычислений.
  Стадия входит в `run`.

**Текущий прогон — `gemini-3.5-flash-lite`, локальный скор 35.0/36 (97.2%), evidence 9/9.**
Не сошлась одна ячейка — P4 6.3 (`ASSUMPTIONS.md`, п. 62). Закрыты две: P8 6.1, где фаза 3 нашла
в примечании сумму строки, оставленной выгрузкой пустой, и P5 6.1, где пункт требует капитальных
затрат **Группы**: они выводятся из движения основных средств в консолидированной отчётности
материнской компании (`ASSUMPTIONS.md`, п. 61). Критик не согласился с одной ячейкой из 36.

Переход на Cerebras `gpt-oss-120b` был сделан и откатан по результату: 28.0/36 против 34.0/36,
разбор шести потерянных ячеек — в `ASSUMPTIONS.md`, п. 13d. Прогон сохранён в
`.cache/prev-cerebras-run/`, вернуться к нему — закомментированный блок в `.env`.

`submit` заполняет шаблон **побайтово через sjson**, а не пересобирает JSON из map: ключи нельзя
переименовать, потерять или добавить. Номера пунктов вроде `6.1` экранируются — иначе sjson принял
бы точку за разделитель пути и превратил ячейку во вложенный объект.
